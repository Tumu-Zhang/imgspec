# 项目管线（组织部维护）

> 本文件是整个仓库的工作规则。四部门是同一位维护者（+AI 助手）在
> 不同工作阶段扮演的角色，目的是让「改代码、发版本、收反馈、做宣传」
> 各有章法、可回溯。规则由组织部统一修订，修订直接改本文件并在 commit 里说明。

## 一、部门与目录

| 部门 | 目录 | 职责 | 典型产出 |
|---|---|---|---|
| 生产部 | `生产部/` | 软件本体：功能开发、缺陷修复、依赖与打包工具维护 | 代码、测试、exe、安装包 |
| 宣传部 | `宣传部/` | 宣传素材与对外发布：截图、收款码、品牌资产、Release 上传 | Release 资产与说明、README 对外内容 |
| 反馈部 | `反馈部/` | 用户反馈与日志的收集、分类、转办、回访 | Issue 模板、反馈处理流程 |
| 组织部 | `组织部/` | 管线规则的制定与修订、跨部门流程仲裁 | 本文件、发布清单、版本规范 |

边界约定：

- `.github/` 是 GitHub 机制目录：CI（`workflows/`）归生产部，Issue 模板
  （`ISSUE_TEMPLATE/`）归反馈部；**位置固定，不可移动**。
- 仓库根只放：README、LICENSE、.gitignore、四部门目录。
- 打包产物（exe、_internal、dist、build）是临时产物，已 gitignore，不进版本库。
- Python 包名（`gui`、`imgspec`）保持英文：import 路径不经过中文，避开工具链编码坑。

## 二、核心工作流

```
反馈 → 需求 → 开发 → 测试 → 发布 → 宣传
```

1. **反馈（反馈部）**：用户 Issue 进来 → 按模板核对信息 → 打标签分类
   （bug / enhancement / question）→ 疑似缺陷转开发。
2. **需求（组织部）**：决定做不做、什么优先级；涉及管线的改动先改本文件。
3. **开发（生产部）**：一个主题一个 commit，改完自测；不混入无关改动。
4. **测试（生产部）**：`cd 生产部 && python -m pytest tests/ -q` 全过；
   涉及打包的改动另跑 build + `--selftest` + `--smoke`。
5. **发布（生产部 → 宣传部）**：按「发布清单」出包，交宣传部上传。
6. **宣传（宣传部）**：Release notes、README 更新、素材归档进 `宣传部/`。

## 三、版本规范

三段式 `主.次.修`（当前 1.0.0）：

- **主 +1**：不兼容的行为或规格语义变更（预期很少发生）
- **次 +1**：新功能、界面大改
- **修 +1**：缺陷修复、小调整

版本号落在两处：Release 的 tag（`vX.Y.Z`），以及出安装包时
`生产部/tools/make_installer.py` 里的 `DEFAULT_VERSION`（发布前手动同步）。

## 四、发布清单（照抄即用）

- [ ] `cd 生产部 && python -m pytest tests/ -q` 全过
- [ ] `python tools\build.py` 打包成功
- [ ] `生产部\图片转换器.exe --selftest` 与 `--smoke` 全过
- [ ] 版本号：Release tag `vX.Y.Z`；出安装包则同步 `DEFAULT_VERSION`
- [ ] Release notes：**新增 / 修复 / 已知问题** 三段
- [ ] 打发布包：`cd 生产部 && python tools\make_release_zip.py`
      （产出 `生产部\dist\release\imgspec-vX.Y.Z-win64.zip`，内含 exe + _internal + README；
      版本号取自 `imgspec.__version__`）
- [ ] 上传后下载一份，解压试跑一遍再标记 latest

## 五、阶段规划

- **阶段一（已完成，2026-10-09）**：四部门布局、PIPELINE.md、Issue 模板、
  反馈与宣传部文档。
- **阶段二（已完成，2026-10-10，v1.1.0）**：「导出日志」按钮（转换日志一键落盘
  txt，头部含版本与系统信息）；「反馈」按钮（打开 Issue 页面）；「检查更新」
  （查 GitHub Releases，发现新版弹提示，可在按钮菜单里关掉启动时自动检查）。
  因国内网络访问 GitHub 不稳定，检查更新按「静默失败」设计：连不上不打扰用户。
- **阶段三（2026-10-10 定案为「零服务器替代」，已实施，v1.2.0）**：日志自动上报
  不做了 —— 需要服务器 + 合规（大陆服务器须 ICP 备案 1-20 工作日 + 公安备案、
  隐私政策、明示同意、路径脱敏），而本项目日志必然含本机文件路径，收益不抵成本。
  替代方案：**会话日志本地落盘**（`%LOCALAPPDATA%\imgspec\图片转换器\logs\`）+
  上次异常退出检测与一键导出。零服务器、零合规负担，只写用户本机、不上传任何数据。
  若将来用户量足够大再评估自建上报（届时按 PIPELINE 流程立项 + 隐私政策评审）。
